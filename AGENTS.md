# Repository Guidelines

## Project Structure & Module Organization

CxShell is a single-project Avalonia desktop terminal and remote session client targeting .NET 11. The application entry points are `Program.cs`, `App.axaml`, and `App.axaml.cs`.

- `Views/`: Avalonia `.axaml` views and their code-behind files.
- `ViewModels/`: MVVM presentation logic, commands, and observable state.
- `Models/`: session, SFTP, and monitoring data objects.
- `Services/`: SSH/SFTP connections, persistence, monitoring, and Linux parsing.
- `Terminal/`: terminal buffer, cells, ANSI parsing, and color handling.
- `Controls/` and `Converters/`: reusable UI controls and binding converters.
- `Assets/`: resources embedded through `CxShell.csproj`.

`AtomUI/` is ignored reference source and explicitly excluded from compilation. Do not treat `bin/` or `obj/` as source.

## Build, Test, and Development Commands

Run commands from the repository root:

```powershell
dotnet restore
dotnet build CxShell.csproj
dotnet run --project CxShell.csproj
dotnet format CxShell.csproj
```

`restore` downloads NuGet dependencies, `build` compiles the app, `run` launches the desktop client, and `format` applies standard .NET formatting.

## Coding Style & Naming Conventions

Use four-space indentation in C# and follow existing file-scoped namespace style. Keep nullable reference types enabled. Use PascalCase for types, public members, views, and view models; use camelCase for parameters and `_camelCase` for private fields. Pair each view with matching names such as `TerminalView.axaml` and `TerminalView.axaml.cs`. Prefer CommunityToolkit.Mvvm attributes (`[ObservableProperty]`, `[RelayCommand]`) over repetitive boilerplate.

## Testing Guidelines

No automated test project currently exists. Before submitting changes, run `dotnet build CxShell.csproj` and manually exercise affected SSH, SFTP, terminal, or monitoring workflows. New test projects should use names such as `CxShell.Tests`, with test files named `<ClassName>Tests.cs`; run them with `dotnet test`.

## Terminal Interaction Requirements

`Controls/TerminalControl.cs` owns terminal-grid interaction. Preserve left-button forward, reverse, and multi-line highlighted selection. Right-click opens the `Popup` in `Views/TerminalView.axaml`, containing Copy and Paste; disable Copy without a selection. Copy writes selected text to the system clipboard. Paste normalizes line endings and sends text through `InputReceived` to the SSH shell at its current cursor. Use Avalonia 12 clipboard extensions from `Avalonia.Input.Platform` (`SetTextAsync`, `TryGetTextAsync`) and catch platform failures. Follow the AtomUI 6.0 manual and local `AtomUI/` reference source for menu styling.

Terminal scrollback is stored by `TerminalBuffer`; `TerminalControl` renders a scroll-offset viewport over that history. Mouse wheel up/down must move through scrollback without sending data to the SSH shell. Hide the cursor while viewing history, preserve selection/copy against the visible viewport, and return to the bottom when the user types, pastes, or sends a key command. If output arrives while the user is viewing history, keep the historical viewport stable instead of forcing it to the bottom.

Unexpected SSH or remote-shell closure must trigger automatic terminal reconnection every five seconds. Successful reconnection stops retries; explicitly closing a tab or disconnecting must cancel them. Treat a zero-byte blocking shell read as remote EOF.

Tabs can be torn out into `Views/DetachedTabWindow`, which hosts the existing tab view model so the session never reconnects. `MainWindowViewModel.DetachTab` unwinds only the main-window bookkeeping and `AttachTab` puts it back; keep the two in sync (property-change subscriptions, tab-group membership, selected tab, companion panels). Dragging a detached window back is conservative: because a native title-bar drag delivers no pointer events, `DetachedTabWindow` polls `Window.Position` plus `GetAsyncKeyState`, and reattaches only when the button is released with the cursor over a visible `TabStrip`/`CardTabStrip` of the main window (falling back to the top 44 DIP band when the main window has no tabs). Dropping anywhere else leaves the window detached, and a successful reattach closes the detached window without disposing the tab.

## Protocol Implementation Notes

Implement protocols incrementally in the agreed order: SSH, SFTP, FTP, TELNET, RLOGIN, SERIAL, then RDP. `Services/IFileTransferService.cs` is the shared backend contract for file browsers; SFTP uses `SftpService`, and plain FTP uses `FtpService` with FluentFTP. `SftpViewModel` selects the service from `SessionInfo.Protocol`, so keep uploads, downloads, rename, delete, and mkdir behavior protocol-neutral. SFTP startup options on `SessionInfo` include local start folder, remote start folder, and custom server command; local/remote folders are active, while SSH.NET still opens the standard SFTP subsystem unless a lower-level custom server implementation is added.

Terminal protocols use `Services/ITerminalConnectionService.cs`. SSH uses `SshConnectionService`; TELNET uses `TelnetConnectionService` with TCP plus TELNET IAC negotiation filtering; RLOGIN uses `RloginConnectionService` with the standard null-delimited startup handshake and terminal window-size message; SERIAL uses `SerialConnectionService` with `System.IO.Ports`. TELNET and RLOGIN password-auth sessions prompt once for a password, then use the configured login prompt strings on `SessionInfo` to auto-send username/password when remote text matches. TELNET session options include XDISPLOC (`$PCADDR` substitution), passive/active option negotiation, and forced character-at-a-time mode via LINEMODE rejection. RLOGIN uses the session username for both local and remote login names. SERIAL stores port name, baud rate, data bits, stop bits, parity, and flow control on `SessionInfo`. RDP is not a terminal protocol; it is rendered by `RdpViewModel` through the native `CxRdpBridge` FreeRDP bridge. The bridge must be built per platform and deployed next to the app or under `runtimes/<rid>/native`. Only SSH tabs should auto-start monitor or SFTP side panels.

SSH X11 forwarding currently uses `ForwardedPortRemote` plus an automatic `DISPLAY=localhost:10.0`-style export to reach a local Windows X server such as Xmanager, VcXsrv, or Xming. This is not a full OpenSSH `x11-req` channel implementation; it depends on remote TCP forwarding being allowed and the local X server listening on the configured display port.

RDP sessions stay alive across idle periods and network drops: the bridge enables TCP keepalive (`FreeRDP_TcpKeepAliveDelay/Interval/Retries`), waits on `freerdp_get_event_handles` with a bounded 25 ms timeout so transport errors surface immediately and queued work is serviced promptly, and reconnects through FreeRDP ARC (`freerdp_disconnect_before_reconnect_context` + `freerdp_reconnect`) with its own retry loop: an escalating 1/2/3/5/10 second backoff, a 20 minute budget, and a user-cancellable "stop trying" path. The SSH tunnel that carries RDP sets `KeepAliveInterval` so NAT devices do not idle it out. Reconnect progress is reported through bridge status lines prefixed `RDP connection lost`, `RDP reconnecting (attempt N)`, `RDP reconnected` and `RDP reconnect failed`; `ViewModels/RdpReconnectStatus.cs` maps them to the localized overlay in `Views/RdpView.axaml`, and the prefixes must stay in sync with `native/CxRdpBridge/cxrdp_bridge.cpp`. When the budget runs out or the user cancels, the view shows a Reconnect button instead of retrying forever.

RDP DPI policy (`SessionInfo.RdpDpiPolicy`, edited in `Views/SessionEditDialog.axaml`): `FollowLocal` (default) maps the local render scaling to a quantized RDP scale (100/125/150/175/200) via `Services/RdpDpiScale.cs`; `Fixed100` forces 100%; `KeepRemote` advertises no scale. At connect time `RdpBridgeClient` calls `cxrdp_set_display_scale`, and the bridge adds the `disp` dynamic channel (registered as `DISP_CHANNEL_NAME` "disp" — the long `DISP_DVC_CHANNEL_NAME` fails to resolve the static addin in freerdp-client3.dll) and sets `FreeRDP_DesktopScaleFactor`/`DeviceScaleFactor`. On resize or a monitored DPI change, `RdpViewModel` calls `cxrdp_update_display`; the bridge queues it on the worker thread, which sends `DispClientContext.SendMonitorLayout` with physical dimensions and then resizes GDI directly (the host's deactivate/reactivate does not emit a Desktop Resize Update). Fall back to the full-reconnect resize path when the bridge lacks API 6 / `CX_RDP_CAPABILITY_RUNTIME_RESIZE`. The C API version is 11 and the smoke tool asserts the runtime-resize capability bit.

RDP connect latency: the bridge tries security profiles in the order `negotiate` (standard X.224 negotiation, what modern servers want) then `nla`, `tls`, `rdp`. Never put the single-layer profiles first — each one costs a complete failed TCP/TLS handshake. `RdpBridgeClient` persists the winning profile per `host:port` in `Services/RdpSecurityProfileCache.cs` (`%LOCALAPPDATA%/CxShell/rdp-security-profiles.json`) after the bridge reports `RDP security profile selected mode=...`, and passes it back through `cxrdp_set_security_profile` (API 7 / `CX_RDP_CAPABILITY_FAST_CONNECT`). A clipboard-triggered retry re-runs only the profile that already worked. Credential/account errors (`ERRCONNECT_LOGON_FAILURE`, `ERRCONNECT_ACCOUNT_LOCKED_OUT`, ...) stop the fallback loop immediately so retries cannot lock an account. `FreeRDP_TcpConnectTimeout`/`TcpAckTimeout` bound each handshake, `cx_retry_dialog` returns -1 during the initial connect (only ARC gets a backoff), and `RdpViewModel` adds a 45 s connect watchdog (`CXSHELL_RDP_CONNECT_TIMEOUT_SECONDS`, 0 disables). Per-profile failures, queued display updates and clipboard retries are classified as transient by `ViewModels/RdpReconnectStatus.cs` — the UI must not treat them as a disconnect; the bridge emits one terminal `RDP connection failed.` line when the loop is exhausted. `SessionInfo.RdpClipboardEnabled` (session edit dialog, default true) maps to `cxrdp_set_clipboard_channel`; `CXSHELL_RDP_CLIPBOARD_CHANNEL=0` remains a global kill switch. Session throughput uses `FreeRDP_CompressionEnabled`, `BitmapCacheEnabled`, `NetworkAutoDetect`, `CONNECTION_TYPE_AUTODETECT` and font smoothing; `SoftwareGdi=TRUE` is required by the GDI frame callback; EGFX (see frame presentation below) is its front end, not an alternative. `SessionInfo.RdpDisableWallpaper` (session edit dialog, default true) maps to `cxrdp_set_disable_wallpaper` (API 9 / `CX_RDP_CAPABILITY_PERFORMANCE_FLAGS`): the bridge sets `FreeRDP_DisableWallpaper` and calls `freerdp_performance_flags_make` so `PERF_DISABLE_WALLPAPER` is folded into `FreeRDP_PerformanceFlags` before the client core data is sent; older bridges lack the bit and the managed side skips the call. The worker keeps a resize queued for 2 s after connect so the `disp` channel can negotiate before a layout is sent; `RdpViewModel` retries an in-place resize once after 1200 ms before falling back to a full reconnect.

RDP frame presentation (`SessionInfo.RdpFrameStrategy`, edited in `Views/SessionEditDialog.axaml`): legacy bitmap updates have NO frame boundary, which is why publishing every `EndPaint` makes the first desktop appear tile by tile. MSTSC and all modern clients solve this at the protocol level with EGFX (MS-RDPEGFX): the server wraps surface commands in `RDPGFX_START_FRAME`/`END_FRAME`, and FreeRDP's GDI backend (`gdi_EndFrame` -> `gdi_OutputUpdate`) copies every decoded surface into `gdi->primary_buffer` and calls `update_end_paint` exactly ONCE per complete logical frame. `cxrdp_bridge.cpp` can enable `FreeRDP_SupportGraphicsPipeline`, `FreeRDP_GfxPlanar`, `FreeRDP_GfxProgressive` and a positive `FreeRDP_FrameAcknowledge` (API 11 / `CX_RDP_CAPABILITY_GFX`, `cxrdp_set_graphics_pipeline`); `SoftwareGdi=TRUE` stays on because EGFX is the FRONT END of the GDI backend, not an alternative to it. **ON BY DEFAULT since 2026-11-23** (`SessionInfo.RdpGraphicsPipelineEnabled = true`): the old black screen was caused by a missing `gdi_graphics_pipeline_init()` binding - the server negotiated EGFX, but decoded surfaces had no GDI target and `EndPaint` never fired. `cx_channel_connected` now binds `RdpgfxClientContext` to the GDI backend, `cx_post_disconnect` unbinds before `gdi_free`, `cx_load_channels` ensures the `rdpgfx` dynamic channel (ADDIN name - see the rule below) and `drdynvc` are present, and PostConnect completes a deferred bind when the DVC opened before `gdi_init`. `CXSHELL_RDP_GFX=1` still forces it on globally. Once bound, `RDP GFX frame mode active.` makes the host publish one complete frame per `EndPaint`, matching MSTSC with no coalescing delay. `cx_post_connect` checks `context->gdi->gfx` and emits the internal `RDP GFX frame mode active.` signal; `RdpBridgeClient.OnStatus` then calls `_frameComposer.Configure(false, true)` so each `EndPaint` snapshot is published immediately as an already-complete frame. **EGFX DVC name rule (this was the last blocker, verified on a real server 2026-11-23):** `FreeRDP_DynamicChannelArray` holds **addin names**, exactly like `"disp"` and `"audin"` - so the graphics channel must be added as `RDPGFX_CHANNEL_NAME` (`"rdpgfx"`), NOT as the wire name `RDPGFX_DVC_CHANNEL_NAME` (`Microsoft::Windows::RDS::Graphics`, 31 chars - it does not even fit FreeRDP's `cName[16]` addin table). Adding the wire name made drdynvc unable to resolve a plugin for the channel, so the connection was aborted with `ERRCONNECT_POST_CONNECT_FAILED` (`0x00020003 category=config`) ~10 ms after `PostConnect`, and the security-profile fallback then surfaced a misleading `ERRCONNECT_CONNECT_TRANSPORT_FAILED`. With `"rdpgfx"` the sequence is `RDP GFX dynamic channels=4 gfxChannel=rdpgfx present=added addin=dynamic` -> `RDP GFX channel connected.` -> `RDP GFX pipeline bound to GDI.` -> `GFX frame mode active`, and the first frame lands with `frame composer first frame presented ... collectMs=5` instead of ~700 ms. `probe_gfx_addin()` resolves the addin through `freerdp_load_channel_addin_entry("rdpgfx", ...)`; when nothing resolves it clears `FreeRDP_SupportGraphicsPipeline`, disables the request and reports `RDP GFX addin unavailable in this FreeRDP build; using legacy bitmap updates.` so a missing addin can never kill the session. As a second line of defence the connect worker treats `POST_CONNECT_FAILED` as non-retryable for other security profiles: it disables EGFX once, re-runs the SAME profile (`break_attempts`) and logs `RDP post connect rejected the graphics pipeline; retrying with legacy bitmap updates.` Never add an EGFX-only retry that walks the remaining profiles - they all fail the same way and just add three doomed handshakes.

**Legacy transport frame markers (preferred over any heuristic):** the bridge now always advertises `FreeRDP_SurfaceCommandsEnabled`, `FreeRDP_FrameMarkerCommandEnabled`, `FreeRDP_SurfaceFrameMarkerEnabled` and `FreeRDP_AltSecFrameMarkerSupport` in the GCC handshake. Without these bits the server never emits `TS_SURFCMD_FRAME_MARKER`, which is why earlier builds always reported `frame markers unavailable`. They are plain capability flags, NOT the EGFX transport, so GDI frame capture is unchanged. `RdpBridgeClient` enables marker probing on every strategy except `Legacy` (including `Coalesce`), starts in coalescing mode, and switches to immediate per-frame publishing only after the first marker arrives; the one-shot `frame markers active/unavailable` status is detected for 3 s of painting. The four strategy modes and the chained `update->SurfaceFrameMarker` handler (API 8) remain as compatibility paths for servers that refuse EGFX. When GFX is NOT negotiated, `RdpFrameComposer` holds the whole repaint wave (first frame AND every later wave) (pure debounce: no periodic publish; 700 ms wave-end quiet, 8000 ms hard cap) instead of trying to guess a frame boundary, and debounces steady updates on the last batch (45 ms interactive updates / 700 ms repaint waves / 8000 ms safety cap; the old 600 ms max-latency publish was removed because it sliced a 6-second repaint wave into visible half-drawn screens). Dirty rectangles (`cxrdp_get_frame_dirty_rect`, API 10) and the 16x9 framebuffer diff in `OnFrame` are diagnostics/fallback only - NEVER use coverage or idle time as a frame boundary. `CXSHELL_RDP_GFX=1` forces the graphics pipeline on globally (it is on per session by default), `CXSHELL_RDP_FRAME_COALESCE=0` disables coalescing, `CXSHELL_RDP_COVERAGE=0` disables the diff fallback. Log keywords: `graphics pipeline requested=`, `GFX frame mode active`, `frame composer first frame presented ... collectMs`; with GFX the first frame correctly appears with `mergedBatches=1` and `collectMs~0` because the protocol already delimited it.

RDP frame presentation latency (regression fix, 2026-11-23): pure repaint-wave debounce must NOT be applied to a live session. The diff-based dirty rectangle is a bounding box, so pointer motion + caret + taskbar clock produce a full-screen rect (`coverage=1.00 wave=True`); a continuous stream then hit the 8 s `MaxLatency` cap once every 8 seconds and the mouse appeared frozen. `Services/RdpFrameComposer.cs` now has three phases: (1) the first frame plus a 10 s `SettlingWindow` with no local input keeps the wave debounce so the initial desktop still appears once, complete; (2) any local pointer/keyboard input flips to immediate publication on the next 16 ms tick (`NoteInteraction` / `IsInteractive`, 3 s idle timeout); (3) after the settling window every fresh framebuffer is published at timer rate, so animations and remote video are not throttled. `RdpBridgeClient` records input with a single `Interlocked.Exchange` on the UI thread and folds it into the composer under `_frameSync` on the presentation timer, so sending a mouse event never waits for a frame-copy lock. `NeedsDirtyRect` skips the sampled full-surface diff outside wave classification, and frame logging is throttled to one line per 2 s so interactive publishing does no synchronous file I/O. Native `cx_end_paint` caps a stalled `BEGIN` frame-marker hold at 120 ms (was 1000 ms) and publishes that batch instead of dropping it. Phase lengths are constructor arguments (`settlingWindow`, `interactiveIdle`); never reintroduce periodic forced publishing inside the settling window.

## Full Screen Connection Bar

`Views/FullScreenConnectionBar.axaml(.cs)` is the mstsc-style floating bar shown at the top centre of a full screen window. It is hosted by `Views/MainWindow.axaml` (bound to `MainWindowViewModel.IsTerminalFullScreen`, endpoint `SelectedTab.Session.Host`, quality `SelectedTab.Rdp.LinkQualityLevel`, `IsQualityVisible=SelectedTab.IsRdpSession`), `Views/DetachedTabWindow.axaml` (bound to the tab view model), `Views/RdpWorkspaceWindow.axaml`, and `Views/RdpMonitorWindow.axaml`. Hosts wire `MinimizeRequested` / `RestoreRequested` / `CloseRequested` / `PinnedChanged` (and workspace/multi-monitor events where applicable).

Behaviour that must not regress:

- The control is always laid out at the top centre but stays `Opacity=0` and `IsHitTestVisible=false`, so it never steals RDP pointer input while hidden. A window-level TUNNEL `PointerMoved` handler (never `e.Handled`) reveals it after the pointer rests 500 ms inside the top 8 px strip within the bar's horizontal span; entering full screen reveals it once so the controls are discoverable. Every reveal starts the same 3 s auto-hide countdown, and the pointer position only extends it: when the countdown expires while the pointer is on the bar the hide is deferred, otherwise a click would land on the remote desktop. Do not use `IsVisible=false` for the hidden state - the bar needs a measured `Bounds` for the hot-zone hit test.
- **Escape does not leave full screen.** The key belongs to the remote session (mstsc behaves the same), so `MainWindow.OnPreviewKeyDown` and `DetachedTabWindow.OnWindowKeyDown` must not consume it for that; the connection bar's restore button (and F11 in a detached window) are the ways out, and `MainWindowViewModel` no longer advertises an `Esc` hint for the full screen command. The old centred ESC toast (`IsFullScreenHintVisible` / `FullScreenEscBackText` / `FullScreen.EscBack`) was removed together with the behaviour, so do not reintroduce one without the other.
- The pin shows two different icons rather than an opacity change: `PinButton` (`PushpinOutlined`) while the bar auto-hides, `PinnedButton` (`PushpinFilled`) while pinned, exactly one of them `IsVisible`. Both share the `OnPinClick` handler and the same tooltip, so the toggle target never moves.
- Pinned keeps the bar on screen (no countdown at all) and is persisted in `ApplicationSettings.FullScreenConnectionBarPinned` through `SessionTreeViewModel.PersistSharedSettings()` (a static helper for UI outside the session tree). Un-pinning starts the usual 3 s countdown.
- The quality bars are an estimate, not an RDP capability: `RdpViewModel` times a bare TCP connect to the session endpoint every 10 s while connected and maps ≤50 ms/≤100 ms/≤200 ms/longer to 4/3/2/1 bars (`LinkQualityLevel`); 0 means unknown/disconnected. RDP exposes no signal strength, and a full reconnect probe must never be used.
- Minimize from the bar leaves the full screen presentation, so the host must restore it when the window comes back: `MainWindow` uses `_restoreFullScreenAfterMinimize` plus `OnMainWindowPropertyChanged`; `DetachedTabWindow` needs `_restoreFullScreenAfterMinimize` / `_restoreKeepTaskbarAfterMinimize` and the `_suppressPresentationRestore` guard, because leaving the taskbar-visible mode changes `WindowState` and would otherwise look like a user restore. Close maps to `CloseTab(SelectedTab)` in the main window and `Close()` in a detached window - never to shutting down the application.
- **Both full screen modes must hide the drawn chrome, not just the title bar.** `WindowState.FullScreen` only drops the native frame; AtomUI draws its title bar (`IsTitleBarVisible`) inside the client area. `Views/KeepTaskbarFullScreen.cs` owns that: `Enter()` hides the title bar before maximizing, the immersive path calls `HideTitleBar()`.
- **AtomUI 6.3.0's built-in full-screen title bar must stay disabled via `FullScreenTitleBarMode="Hidden"`.** AtomUI 6.3.0 removed `FullscreenHeaderFrame` from `WindowDrawnDecorationsTheme` and introduced `Window.FullScreenTitleBarMode` (default `AutoHide`) inside `WindowChromeLayer`. Every window hosting `FullScreenConnectionBar` (`MainWindow.axaml`, `DetachedTabWindow.axaml`, `RdpWorkspaceWindow.axaml`, `RdpMonitorWindow.axaml`) must set `FullScreenTitleBarMode="Hidden"` so AtomUI never activates its built-in full-screen bar or moves `TitleBar` between `NormalSlotTitleBar` and `FullScreenSlotContent`.
- **Keep `FullScreenConnectionBar` as a dedicated control rather than replacing it with `Window.FullScreenTitleBar`.** `Window.FullScreenTitleBar` only activates for `WindowState.FullScreen`, whereas CxShell needs the same bar in taskbar-visible maximized mode (`KeepTaskbarFullScreen`) and `RdpMonitorWindow` borderless mode, with the centred 8 px / 500 ms mstsc hot-zone, RDP link quality, pin persistence, multi-monitor popup lock, workspace tab switching, and drag-restore.
- `KeepTaskbarFullScreen` owns `HideTitleBar`/`RestoreTitleBar` and `HideDecorations`/`RestoreDecorations` (`Window.WindowDecorations = None`, previous values saved once). Both helpers are idempotent so switching between "keep taskbar" and immersive full screen never loses the original state. Restore them on every exit path (after leaving full screen, never before), including an external takeover (window manager shortcut, native caption button): `MainWindow.OnMainWindowPropertyChanged` and `DetachedTabWindow.OnWindowPropertyChanged` restore the chrome whenever the window ends up outside full screen without `_keepTaskbarFullScreen.IsActive`. Never bind `IsTitleBarVisible` or `WindowDecorations` from XAML.

## X/Y/ZMODEM File Transfer

`Services/ZmodemTransfer.cs` implements `rz`/`sz` in pure C#, and `Services/XymodemTransfer.cs` implements XMODEM/YMODEM upload and download in pure C#; do not reintroduce Node, `zmodem.js`, or `zmodem4dotnet` runtime dependencies. `SshConnectionService` exposes raw binary shell data via `BinaryDataReceived`; `TerminalViewModel` detects ZMODEM startup headers and hands the byte stream to `ZmodemTransfer`.

Remote `sz <file>` must prompt for a local folder, download the offered file, swallow the ZMODEM `rz` preamble, high-bit header terminators (`0x8a`, `0x8d`) and XON/XOFF padding, then wait for and consume the final remote `OO`. Remote `rz` must prompt for one or more local files and upload them at the current remote shell location. Keep ZMODEM status messages plain text to avoid ANSI artifacts during binary transfers.

For X/YMODEM, `TerminalViewModel` recognizes `rx` as XMODEM upload, `rb`/`ry` as YMODEM upload, `sx <file>` as XMODEM download, and `sb <file>` as YMODEM download. X/YMODEM downloads must wait for the remote "Give your local ... receive command now" prompt before sending local receiver handshakes. X/YMODEM transfers use the same configured download/upload directories and duplicate-file policy as ZMODEM where applicable.

## Commit & Pull Request Guidelines

History currently contains only `first commit`, so no established commit convention exists. Use short imperative subjects, for example `Fix SFTP directory refresh`. Keep commits focused. Pull requests should describe behavior changes, list verification steps, link relevant issues, and include screenshots for visual Avalonia changes. Never commit credentials, private keys, session data, or generated `bin/` and `obj/` output.
